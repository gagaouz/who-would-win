## Scope and preservation rule

Version 2.0 is the whole game in the retro visual language. There is no classic theme selector in 2.0. The 1.1.7 branch preserves the old presentation and its hotfix path. Every reachable flow below must remain usable in 2.0, with equivalent entitlements, saved progress, results, learning content, parental controls, rewards, and purchase behavior. Screens, sheets, loading states, errors, shared images, and accessibility representations are part of the theme work; replacing only the duel screen does not satisfy this contract.

Source paths beginning with `ios/` are relative to the repository root; abbreviated paths such as `Services/` and `Views/` are relative to `ios/WhoWouldWin/`. Line numbers refer to the audited baseline and will move during implementation. Where comments conflict with executable code, this document follows code. Existing defects are called out separately: preserving features does not mean quietly reproducing a known defect or silently changing the economy.

### Cloud behavior that must be tested, not assumed

`Services/CloudSyncService.swift:28–79` uses MAX merge for counters **and coin balance**, TRUE-wins for permanent flags, UNION for achievement string arrays, and per-key MAX for animal wins. Subscription is correctly excluded from TRUE-wins. `collected.animals`, `iap.melee`, tournament saves, many local preference/daily/custom flags are absent from its tracked lists. Therefore the current implementation does not back up every piece of progress.

MAX-merging a spendable balance can restore previously spent coins. TRUE-wins entitlement flags also cannot represent a later revocation independently from earned ownership. The restore method writes UserDefaults and posts `CloudSyncDidRestore`; this audit found no consumer of that notification in iOS source. Already-initialized observable singletons may not reflect merged values immediately. These are source-derived hazards requiring runtime reproduction and a deliberate migration/repair decision. Do not call existing cloud sync complete or silently replace its semantics while re-theming.

## Reachable behavior versus dormant or stale material

- Current entry is `KidsHomeView`. `KidsChampionView` has no discovered app call site; old `BattleShareCard` is not the active normal share renderer. Active exports are `KidsShareCard`, `MeleeShareCard`, and `TournamentShareCard`. Preserve working capabilities, not unused old screens for their own sake.
- README/comments mention SpriteKit, but there is no remaining SpriteKit scene directory/class. Current duels and melees use SwiftUI presentation plus a six-second gate. A retro animator replaces that presentation while honoring asynchronous results/cancellation; it does not inherit an existing combat engine.
- Tournament quick-mode comments say “skip API”; executable code uses `/api/battle/quick`, or the optional on-device experiment when eligible. It is not a guaranteed instant/local result.
- Melee model comments mention up to six and services accept environment/custom arguments, but the reachable setup is 1–4 built-in fighters per side and launches without arena selection. No custom creator is wired into that setup. Expanding those capabilities is new scope, not baseline parity.
- The unused tournament 25-coin custom constant and comments about charging at bracket commit are stale. Reachable picker charges 150 on add.
- Arena comments mention rewarded one-try access; current `KidsPreBattleView` ignores taps on locked tiles. No one-try ad route is wired there.
- `pref.lightMode` exists, but the UI explicitly removed that control and the app forces light appearance. 2.0 needs no classic/light-mode compatibility UI.
- Optional parental PIN protects wagering-setting changes in the Grown-Up Zone. It is not the universal purchase gate; purchase/external-link gates currently use fresh multiplication challenges.
- There is no general persisted battle-history screen/model in current source. Personal progress consists of counters, animal wins, stickers and achievements; an active tournament contains its match results and ledger. Hall of Fame is a cached aggregate server leaderboard, not personal history. A new replay/history library must not be presented as an existing feature.
- Only normal duel result code collects both animals, records individual wins/prediction stats, and runs general battle-achievement checks. Melee result currently records battle count and coins. Tournament saves results and tournament achievements but has no discovered `recordBattle`/`earnBattleCoins`/`collectBoth` call for each match. Do not accidentally change progression by sharing result components without a documented mode-specific event contract.

## Existing defects and high-risk regression seams

These findings are **SOURCE OBSERVATIONS — NOT RUNTIME REPRODUCED**. Record the chosen repair in the implementation plan, and add targeted tests if touched.

1. **Reward ownership is distributed across view lifecycle callbacks.** Normal duel result has its own side-effect guard; melee awards in result `.onAppear` with no equivalent visible guard. Tournament payout guards are persisted, but coin writes and tournament flag/ledger writes are separate operations. New navigation or share-sheet presentation can expose duplication. Centralize a deliberate exactly-once completion contract before widespread view restructuring. References: `Views/KidsBattleView.swift:998`; `Views/Melee/MeleeBattleView.swift:40`; `Services/TournamentManager.swift:446`, `:554`.
2. **Upgrade decode must preserve an in-progress paid bracket.** Current loader deletes any unrecognized schema/decode failure. Custom fighters and stored URLs live inside Codable tournament objects; adding sprite metadata must be optional/defaulted or migrated. Reference: `Services/TournamentManager.swift:26`; `Models/Tournament.swift:142`.
